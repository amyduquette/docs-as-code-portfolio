# Add product integration docs to another repository

Run this workflow in the target repository: the third-party tool's documentation repository. Resolve source-documentation paths against the separate source docs checkout, not the current working directory. If its location is unknown, ask before gathering source material. Point the agent at this skill explicitly when working outside the repository that contains it; do not assume cross-repository discovery.

For integration pages in the source product's own docs, use [add-tool-page](../add-tool-page/SKILL.md) instead. The paths and command names below are fictional examples; map them to the source project before use.

## Source of truth

Pull facts from the source product's documentation checkout, not from memory or the target repo's existing prose about the product. Build a source map before drafting. For example:

- `tools/*.mdx` and `tools.mdx`: per-tool setup instructions and the current integration index. Check coverage before assuming a dedicated page exists.
- `tools/other-acp.mdx`: generic Agent Client Protocol (ACP) setup for editors without a dedicated page. Verify exact CLI flags before adapting them.
- `cli/install.mdx` and `cli/cli-reference.mdx`: install commands, authentication paths, flags, and environment variables for the agent CLI (`example`). Keep hosted-service, organization-deployment, and third-party-provider authentication distinct.
- `get-started/sign-in.mdx`: guidance for choosing an authentication method.
- `models/supported-models.mdx`: current model facts, when the target repository actually needs that specificity. Do not use release notes drafted from the same facts packet as independent evidence.
- [Writing standards](../../docs-standards/STYLE_GUIDE.md): the source product's terminology. For the target product and page structure, follow the target repository's own conventions.

Treat command syntax, JSON/config examples, and prerequisite steps from these files as a starting point, but still reconcile them against the target platform's actual paths, config schema, and supported OS list. A source page can be accurate about the product and still wrong about how the target platform's config file is named or where it lives cross-platform.

For anything the reader will actually run (install commands, CLI invocations, config that gets pasted verbatim), verify against the owning product source repository's actual implementation when it's accessible, the same bar [add-tool-page](../add-tool-page/SKILL.md) and [review-docs](../review-docs/SKILL.md) hold runnable claims to. Don't treat a source page's clear, confident prose as sufficient on its own just because it isn't ambiguous; docs can describe intended behavior that no longer matches what a script or command actually does. If these pages are ambiguous or silent about the exact product behavior you need (not the target platform's behavior, but the source product's own), consult the owning product source repository for the same reason: the source project's own guidance should identify which implementation owns that behavior. Do not guess past a real gap; leave it as an open question in your report instead.

## What not to trust from the source pages

Source pages describe the source product's own docs and setup steps. They do not reliably describe the *target platform's* current state. In particular:

- **Never infer registry/marketplace availability from what the source page documents.** A source page showing manual or CLI-based setup does not mean the target platform lacks a registry/marketplace listing: it may just predate one, or the page may not cover every install path. Verify availability against the target platform's live registry, marketplace, or extension listing before writing an availability claim (positive or negative).
- Don't assume the source page's file paths, env vars, or settings locations are platform-universal. Check whether the target repo documents OS-specific variants (Windows vs. macOS/Linux) for the same concept, and match that pattern if it exists.
- Do not treat a source page's section structure as evidence for the target repository's structure. Source pages provide facts about the source product; sibling entries provide the structure. When the same device has different meanings in each repository, such as tabs representing access paths in the source and editors or clients in the target, use the target repository's meaning.

## Workflow

1. **Inspect the target repo.** Read its `AGENTS.md`/`CLAUDE.md`/style guide equivalent, `CONTRIBUTING.md`, and pull request template when present. Then inspect any pending changes already in flight and at least three existing sibling entries for other providers/tools/agents in the same file or files. The goal is a structural and phrasing template, not just tone. Specifically check whether `CONTRIBUTING.md` or its equivalent gates new *built-in* integrations behind a discussion or issue before a PR. This requirement is common in maintainer-curated plugin ecosystems. If it does, and the requester hasn't said that's already been cleared, treat adding a new built-in integration as out of scope for a docs task, even when the target repo would technically accept the code. Built-in work includes a new source file, a registration or config entry, or a first-class "Setup: X" section listed alongside other built-ins. Default to documenting the product through the target repo's existing bring-your-own-config, custom-provider, or user-defined extension point. Use the same mechanism that its docs recommend for unlisted tools. Ask the requester which path they want if the repo has more than one and the correct choice is unclear.
2. **Identify the integration surfaces.** Registry/marketplace install, a CLI the user installs and runs (`example acp`), manual custom-agent/config entry, a native extension, generic API-provider access, and terminal-only use are distinct paths with distinct auth, install, and billing boundaries. Do not collapse them: a target repo's docs pattern usually already separates "hosted/registry," "custom/manual," and "run in terminal" as different rows or sections.
3. **Gather facts** from the source-of-truth list above, plus the target platform's live state (its actual registry contents, current source code or settings schema, changelog) for anything platform-specific.
4. **Build the target structure, then draft in it.** Complete these substeps in order:
   - **Characterize the entry and find analogs.** Before drafting, characterize the new entry's shape: how many distinct access paths, auth models, or install surfaces it has. Then find every sibling that shares that shape, scanning the whole directory for the closest structural analog instead of sampling by frequency.
   - **Handle multi-surface entries as a distinct shape.** Multi-surface entries usually need a different skeleton than single-surface ones: an up-front chooser section, then one section per surface, each repeating the same credential and configuration subsections. Most sibling entries document a single surface, so that skeleton is typically the minority pattern in the directory and will not appear in a sample drawn by frequency. Find the repo's own version of it before defaulting to the common template.
   - **Build the heading skeleton from analogous siblings.** Extract the analogous siblings' H1/H2/H3 sequences into a heading skeleton, even when fewer than three analogous siblings exist. Inspect at least three siblings total, but use additional nonanalogous siblings only to check the directory's breadth and metadata patterns, not to classify headings in the analogous skeleton. Mark each heading as fixed when it appears in every analogous sibling or optional when it appears in only some, and record repeated non-heading template elements such as a website/link line. When no analogous sibling exists, derive the skeleton from at least three siblings and use the majority pattern.
   - **Derive metadata formulas from the whole directory.** For each frontmatter or list-entry field siblings share, such as title, description, or summary, derive the phrasing formula they follow rather than only noting the field exists. Sample these fields across the whole directory to find the general formula, then check whether the new entry's own section or nav group runs a consistent variant. When it does, the group's variant wins over the repo-wide majority, since these conventions often cluster by section even when the underlying formula holds everywhere. These formulas usually carry required content, for example naming what the models actually are instead of restating the vendor's name, and stating which surfaces the setup covers. Write the new entry's fields to the selected formula.
   - **Draft from the skeleton and record precedents.** When the closest analog is a minority pattern in the directory, it still wins over the majority template; say so in the report. Only when no analog exists does the majority template become the skeleton. Draft against the skeleton and reproduce every fixed heading and template element. Deviate from it only when a named sibling provides a precedent, and cite that sibling in the skeleton and final report.
   - **Prioritize the target-native path and required cross-references.** Make the target-native default path (registry/marketplace install, when one exists) primary; keep CLI setup and manual config as documented alternatives, matching how the target repo already presents other providers' registry-vs-manual paths. Update cross-reference points (frontmatter descriptions, index/list pages, cross-link sentences) only where the target repo's own pattern requires it for that entry to be found; compare against how sibling entries are cross-referenced rather than mechanically touching every list that mentions another provider's name.
5. **Validate.** Exact commands and config blocks against the source pages; internal/external links and anchors; the target repo's own pinned formatter/linter version (not whatever's on `PATH`); and the target repo's build/check commands if it has them (for example, `git diff --check`). Check the target repo's own convention for when to run these: some expect local validation before every review pass; others route checks through CI or reserve local checks for a specific handoff. Don't assume either default; look for it.
6. **Build a fact ledger during verification**, not in the published doc: for each factual claim (especially availability/registry claims and auth-ownership claims), note the claim, which system owns that fact, the source checked, and when it was checked. Keep this in working notes or the task report, not in the shipped page. Where possible, get a second, independent check on availability-style claims specifically: same-agent self-review is structurally weak at catching errors caused by trusting the source document's framing.
7. **Report** what was sourced from where, what was verified against live target-platform state vs. taken from source docs as-is, formatter/validation results, and any unresolved product or SME questions (for example, auth model nuances, or whether a feature is GA). Include the sibling heading skeleton used, the headings written, and every deviation with its named sibling precedent.

## Guardrails

- Never state or imply registry/marketplace availability (positive or negative) without checking the target platform's live state.
- Keep the agent, agent CLI (`example`), model family, and API-provider access distinct. Don't let one stand in for another.
- Don't summarize auth as a single account/API key when the source documents multiple paths (hosted-service auth, organization-deployment browser/token auth, and third-party provider credentials).
- Treat install/auth prerequisites as specific to the path being documented (registry install may not need the same prerequisites as CLI setup).
- When linking to installation instructions from another repository, use the project's designated stable installation entry point. Confirm that contract with the source project rather than choosing a deep documentation path by habit.
- Link to the most stable target that still answers the reader's question, and never point a cross-repository link at an anchor. This applies to links leaving the target repo, including links into our docs; anchors within the target repo's own pages are fine and are covered by its link checking. Anchors break whenever a heading is edited, deep paths break whenever pages are reorganized, and repository-local checks may miss those changes: confirm whether the target checker validates external destinations, since the source project may not see inbound links from the target repository. Prefer a section entry point over a specific page when both work. When the reader needs one specific procedure, endpoint, command, or field, name it in prose and link the stable parent page, so the sentence still tells them what to look for after the link moves.
- Avoid stating a single settings/config file path as platform-universal unless verified for every OS the target repo documents.
- Include only details users need to complete the integration. Link to canonical docs instead of repeating fast-changing model lists, pricing, versions, availability counts, benchmarks, or other incidental details. If a volatile detail is necessary, verify it against the live source and record it in the fact ledger.
- After drafting, diff the draft's H1/H2/H3 list and its metadata fields against the fixed headings and phrasing formulas in the sibling skeleton. Check especially for fixed elements that have no counterpart in the source page, including website/link lines, tips or notes sections, and troubleshooting. Fold trailing orphan paragraphs, including prose after a tab block, into the section the target template provides for them.
- Format with the target repo's pinned tool version, not an ambient global install.
- Prefer minimal, non-promotional, factual copy that mirrors existing sibling entries over introducing new phrasing patterns.
- A new source file, module, or config-registration entry in the target repo's code is a feature contribution, not documentation. Treat it that way even when it ships alongside a docs section or closely mirrors an existing sibling integration. Don't add one by default. Use the target repo's existing custom or user-defined extension point unless the requester confirms that the approval requirement for new built-ins is already satisfied through a discussion, issue, or maintainer sign-off.
